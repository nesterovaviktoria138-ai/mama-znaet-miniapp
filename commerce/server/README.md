# Сервер оплаты «Мама знает»: подготовлено, продажи выключены

Это отдельный Python 3.11+ WSGI-модуль. GitHub Pages его **не запускает**.
Он пока не подключён к интерфейсу приложения, реальному боту или хостингу.
`LAUNCH_READY = False` намеренно блокирует создание счетов и новые pre-checkout.
Даже включение `sales_enabled` в каталоге не откроет продажи.
Существующие уведомления об уже совершённых покупках и возвратах обрабатываются
независимо от выключателя продаж.

## Что реализовано

- Проверка HMAC `Telegram.WebApp.initData`, срока подписи (час) и ID пользователя.
  `initDataUnsafe`, ID из формы и отметка клиента «оплачено» не принимаются.
- Четыре продукта из `commerce/catalog.json`. Цена и набор разделов копируются
  в заказ на сервере; рублёвые ориентиры никогда не используются как сумма XTR.
- Подготовка одноразового `createInvoiceLink`, без subscription_period.
- Проверка покупателя, валюты, суммы, срока счёта и повторного pre-checkout.
- Доступ выдаётся только по проверенному `successful_payment` из webhook
  с отдельным секретом. Срок: 12 календарных месяцев от даты оплаты UTC;
  29 февраля превращается в 28 февраля следующего года.
- SQLite хранит заказы, согласованную версию условий, суммы, charge ID и возвраты.
  Транзакции предотвращают двойную выдачу при параллельных уведомлениях.
- Повтор доставки не продлевает доступ. Возврат закрывает соответствующую
  покупку, сохраняя другие. Возврат раньше уведомления об оплате тоже учитывается.
- Неожиданный второй charge по одному заказу записывается с deliverable=0
  для ручного разбора и возврата, без второго предоставления доступа.
- `/api/access` возвращает только разделы проверенного пользователя и сроки.
  Этот endpoint сам по себе не защищает публичные материалы приложения.

## API

- `GET /health` — техническая готовность процесса, не готовность продаж.
- `POST /api/access` — JSON `{ "init_data": "..." }`.
- `POST /api/invoice` — JSON с `init_data`, `product_id`, `accepted_terms`.
  Сейчас всегда отклоняется. После интеграции возвращает `invoice_url` для
  `Telegram.WebApp.openInvoice`; результат окна не выдаёт доступ.
- `POST /telegram/webhook` — Telegram update и заголовок
  `X-Telegram-Bot-Api-Secret-Token`. Повторяемые ошибки возвращают не-2xx.

## Настройка хостинга — ещё не выполнена

Нужен HTTPS-хостинг Python с постоянным диском, резервным копированием SQLite
и production WSGI-сервером. Нельзя использовать временный диск serverless-функций
или несколько независимых копий базы. Для масштабирования нужна общая СУБД.

В защищённых настройках хостинга задаются:

- `TELEGRAM_BOT_TOKEN` — токен BotFather. Не помещать в чат, GitHub, HTML или JS.
- `TELEGRAM_WEBHOOK_SECRET` — случайный секрет длиной минимум 32 символа,
  из допустимых Telegram символов `A-Z a-z 0-9 _ -`.
- `PAYMENTS_DB` — абсолютный путь на постоянном диске, например
  `/var/lib/mama-payments/payments.sqlite`. Родительская папка должна существовать.
- `TERMS_VERSION` — версия опубликованных условий после их подготовки.

Точка входа WSGI: `commerce/server/wsgi.py`, объект `application`.
Модуль завершает запуск с ошибкой при отсутствии обязательных секретов или пути.
Веб-сервер должен ограничивать размер тела (64 КиБ), время чтения, частоту
запросов и не писать initData, webhook payload или токен в журналы.
Для pre-checkout Telegram даёт 10 секунд; исходящий запрос ограничен 5 секундами.
На хостинге нужно проверить суммарную задержку под нагрузкой.

Регистрация webhook должна выполняться отдельно, после развёртывания и проверки,
с `secret_token`, `allowed_updates: ["message", "pre_checkout_query"]`.
Не сбрасывать ожидающие события (`drop_pending_updates=false`).
В этой работе регистрация webhook и вызовы реального Bot API **не выполнялись**.

## Обязательные шаги перед снятием LAUNCH_READY

1. Утвердить реальные целые цены в Stars; сейчас `stars: null`.
2. Разместить сервер, подключить секреты, постоянную базу и проверить её восстановление.
3. Реализовать защищённую выдачу материалов/расчётов и связать интерфейс с `/api/access`.
   Сейчас JS, старые копии и архивы доступны публично на GitHub Pages.
   Проверки только в браузере не защищают платный контент; опубликованная история
   GitHub также останется доступной. Нельзя объявлять текущую версию защищённой.
4. Опубликовать условия, контакт продавца и поддержку; добавить обработку
   `/terms`, `/support`, `/paysupport` и согласие перед счётом.
5. Подключить операции возврата `refundStarPayment` через защищённый операторский
   интерфейс, сверку `getStarTransactions` и мониторинг ошибок/charge с deliverable=0.
   Сейчас реализовано получение уведомлений о возврате, не инициирование возвратов.
6. Сохранить просмотр и экспорт личных записей без действующей подписки;
   оставить бесплатную информацию об экстренных ситуациях.
7. Пройти E2E в тестовой среде Telegram: покупка, отмена, задержка уведомления,
   повтор, возврат, восстановление базы, открытие с другого устройства и истечение срока.
8. Только после этого снять программный блок и включить каталог.

Политика текущего прототипа: активный полностью покрытый продукт нельзя купить
повторно. Покупка полного доступа при наличии отдельного даёт новый срок полного
доступа от новой покупки; доплаты, скидки и суммирование сроков не реализованы.
Перед запуском эти правила нужно явно отобразить в предложении покупателю.

## Проверки

Из корня репозитория:

```sh
python -m unittest discover -s commerce/server -v
```

Тесты используют только временные базы, вымышленные токены и цены. Проверены
подмена и устаревание подписи, границы доступа, четыре продукта, дубли/параллельная
доставка, подмена суммы/валюты/покупателя, возврат и порядок событий, сохранение
данных при перезапуске, високосная дата, секрет webhook и блокировка продаж.
Это локальные автоматические проверки, не реальные платежи Telegram.

Официальная документация, проверена 13.10.2026:

- https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app
- https://core.telegram.org/bots/api#successfulpayment
- https://core.telegram.org/bots/api#refundedpayment
